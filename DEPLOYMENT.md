# NTT Nutrition RBM — Free Web Deployment (Render + Neon)

## Current status
- Source code, authentication, read-only public dashboard, and React-free Flask backend are in this GitHub repository.
- \`render.yaml\` now requests **Render Web Free**, not a paid service.
- PostgreSQL is an **external Neon Free database**; no Render PostgreSQL instance is provisioned.
- The public URL is **not live** until the Neon database and Render web service are connected and deployed.

## Step 1 — Set up Neon Free database
Create a Neon project on the **Free** plan. Choose a region near your audience and the Render Singapore service if possible. Obtain a **pooled** PostgreSQL connection string through the Neon dashboard. Prefer a role with only the necessary permissions, restricted to the application's database.

**Never commit DATABASE_URL, a Neon connection string, the database password, or RBM_ADMIN_PASSWORD to this public GitHub repository.** Store secrets only in the Render Environment tab or a secure secrets manager. Avoid posting them in a chat or issue.

## Step 2 — Render Free web service
The Blueprint URL:
https://dashboard.render.com/blueprint/new?repo=https://github.com/fandiimran3012-design/ntt-nutrition-rbm-dashboard

The Blueprint asks for these **manual secrets** on the Render website:
- \`DATABASE_URL\` — copy from Neon, **never from a screenshot in a public channel**
- \`RBM_ADMIN_PASSWORD\` — choose a long, random password

Additional settings:
- \`SECRET_KEY\` is generated by Render.
- \`RBM_REQUIRE_POSTGRES=true\` stops the app from silently using an ephemeral SQLite database.
- \`RBM_REQUIRE_HTTPS=true\` sets secure cookies behind Render HTTPS.
- Set \`RBM_ADMIN_PASSWORD\` privately before deployment, not in repository code.

**Note:** Render may show \`need_payment_info\` for this workspace **even for the Free plan**. If this persists, verify Render account billing requirements in the provider Dashboard. Adding a payment method does not mean choosing a paid plan, but inspect your selected plan and all billable options before accepting.

## Step 3 — Review before publishing
This prototype uses a shared administrator password, not UNICEF SSO or individual user accounts. Get organizational IT / Infosec approval before loading personal or sensitive programme information. Public-view filtering is basic and not independently security-audited.

Ensure only the intended aggregated metrics are made public. Do not upload participants' names, beneficiary records, phone numbers, or confidential evidence links. Restrict access to saved JSON backups.

## Step 4 — Post-deployment tests
- Open \`https://YOUR-RENDER-SERVICE.onrender.com/api/health\`; confirm \`status=ok\` and \`database=postgresql\`.
- Open \`/\` in an incognito window and verify read-only access.
- Open \`/login\` and sign in as the editor.
- Add a test activity, confirm it persists, then open the public viewer from a second browser. Updates are polled approximately every 15 seconds.
- Check that the public API never exposes internal-only notes or links.
- Export multiple private JSON backups before migrating actual data.

## Step 5 — Import previous RBM data
The older HTML dashboard may have stored updates in its local browser storage. Open the exact browser/device used for data entry, then click **Backup Data (JSON)**. Keep this backup before switching to the live site. After deployment, sign in on the new site and import the JSON, then verify programme mappings and historic SACA indicator revisions carefully.

## Free-plan limitations
Both Render Free and Neon Free have usage quotas, service limitations, potential inactivity behaviour, and no promise of perpetual free hosting. Web requests may be slower on cold starts. Keep regular exports/backups and do not rely on free-plan uptime for critical programme operations.
